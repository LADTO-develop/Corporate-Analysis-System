# 5에이전트 기반 신용위험 검토 구조 설계

## 1. 목적

본 문서는 상장기업 신용위험 조기경보 프로젝트의 후속 단계에서 사용할
5에이전트 기반 검토 구조를 정리한 설계 문서이다.

프로젝트는 다음의 2단 구조를 기본으로 설계한다.

1. XGBoost 기반 정량 예측
2. 5에이전트 기반 종합 검토

즉, 정량 예측은 모델이 담당하고, 해석·검증·정성 보완·최종 심사 메모 작성은
다중 에이전트가 담당하는 구조를 목표로 한다.

## 2. 기본 원칙

본 구조는 **정량 모델의 원본 판단**과 **에이전트 기반 종합 검토 의견**을 분리하는 것을 기본 원칙으로 한다.

### model_view
- XGBoost 기반 원본 판단
- 예측확률(`y_proba`)
- 모델 라벨: `투자적격` / `부적격`
- 위험 밴드
- SHAP 기반 주요 변수

이 값은 모델의 원판단으로 간주하며, Agent나 LLM이 직접 수정하지 않는다.

### committee_view
- 5개 에이전트가 외부 정보와 정성 근거를 검토한 뒤 제시하는 종합 의견
- 위원회 라벨: `적격` / `보류` / `부적격`
- 모델 판단 유지 여부, 경계 의견, 추가 점검 필요 여부 등을 설명형 의견으로 제시

즉, 최종 결과는 **모델이 본 이진 판단(model_view)**과
**위원회가 검토한 3단계 종합 의견(committee_view)**을 함께 보여주는 구조로 설계한다.

## 3. 단계별 구조

### Stage 1. 정량 예측 단계

XGBoost 모델이 기업의 재무제표 기반 핵심 변수와 거시 변수를 활용하여
해당 기업의 투기등급 위험확률(`y_proba`)을 산출한다.
이 확률값을 기준으로 모델은 기업을 `투자적격` 또는 `부적격`으로 분류한다.
이 값은 모델의 원본 판단으로 간주하며, 이후 단계에서 직접 조정하지 않고
`model_view`로 보존한다.

주요 산출물:
- 예측확률(`y_proba`)
- 모델 라벨 (`투자적격` / `부적격`)
- 위험 밴드
- SHAP 기반 주요 영향 변수
- 핵심 재무지표
- 시장/산업 비교 결과

### Stage 2. 5에이전트 검토 단계

에이전트들은 `model_view`를 입력받고, 기업 관련 외부 정보를 수집·검토하여
각자의 관점에서 의견을 제시한다.
이 단계의 목적은 모델 결과를 덮어쓰는 것이 아니라,
**정량 결과를 설명하고 보완할 정성적 근거를 축적하는 것**이다.

에이전트 구성은 다음과 같다.

#### 1. FinancialModelAgent

역할:
- XGBoost 결과와 SHAP 기반 주요 변수 해석
- 핵심 재무변수와 산업/시장 비교 결과를 바탕으로
  모델이 왜 해당 판단을 내렸는지 설명

입력:
- 예측확률
- 모델 라벨
- SHAP 상위 변수
- 핵심 재무지표
- 시장/산업 비교 결과

출력:
- 정량 해석 요약
- 핵심 위험 요인
- 완화 요인

#### 2. DebtLiquidityAgent

역할:
- 부채상환능력, 유동성, 현금흐름, 단기 방어력 검토
- 재무적으로 실제 버틸 수 있는 체력과 위험 신호 점검

입력:
- 부채 관련 핵심 지표
- 유동성 관련 지표
- 현금흐름 관련 지표

출력:
- 부채상환능력 평가
- 유동성 리스크 요약
- 현금흐름 관점의 보완 의견

#### 3. MacroMarketAgent

역할:
- 금리, 환율, 회사채 스프레드, 시장 환경 등 거시 요인 검토
- 현재 위험 수준이 외부 시장환경 변화에 따라 어떤 영향을 받을 수 있는지 설명

입력:
- 현재 금리
- 환율
- 회사채 스프레드
- 관련 시장·거시 참고 지표

출력:
- 거시환경 요약
- 현재 시장 여건이 기업 위험도에 미치는 영향
- 외부 충격 민감도 의견

#### 4. EvidenceAuditAgent

역할:
- 뉴스, DART 공시, 재무제표 주석 등 외부 근거를 수집하고 검증
- 근거의 신뢰도를 구분하고, 중복·루머·저신뢰 정보를 걸러냄
- 다른 에이전트들이 공통으로 활용할 evidence bundle 정리

입력:
- 기업 관련 뉴스
- DART 공시
- 재무제표 주석
- 외부 참고 자료

출력:
- 핵심 사건 요약
- 근거 신뢰도 정리
- 중요 공시 및 뉴스 팩트 목록

#### 5. ChairInvestmentAgent

역할:
- 각 에이전트의 의견을 종합하고 최종 투자적격성 의견을 정리
- 모델 원판단과 정성 검토 결과를 함께 고려하여 종합 메모 작성
- 최종 위원회 라벨을 `적격` / `보류` / `부적격` 중 하나로 제시

입력:
- FinancialModelAgent 결과
- DebtLiquidityAgent 결과
- MacroMarketAgent 결과
- EvidenceAuditAgent 결과

출력:
- 최종 위원회 라벨 (`적격` / `보류` / `부적격`)
- 주요 위험 요인
- 완화 요인
- 종합 심사 메모

## 4. 회의 진행 구조

5에이전트 회의는 다음과 같은 3라운드 구조로 진행한다.

### 1라운드: 초기 의견 제시

각 에이전트가 자신의 관점에서 최초 의견을 제시한다.

- FinancialModelAgent: 정량 모델 해석
- DebtLiquidityAgent: 재무 방어력 진단
- MacroMarketAgent: 시장환경 영향 해석
- EvidenceAuditAgent: 외부 근거 요약

### 2라운드: 상호 검증

에이전트들이 서로의 주장에 대해 근거 부족, 해석 오류, 과도한 일반화 여부를 검증한다.
이 단계에서는 모든 의견을 무한정 토론하기보다,
**충돌하는 쟁점이나 핵심 차이**를 중심으로 검토한다.

예시:
- 정량상 `투자적격`으로 보이지만 외부 공시상 위험 신호가 큰 경우
- 현재 유동성은 안정적이나 시장환경 악화에 취약한 경우
- 뉴스상 우려가 있으나 공시 근거는 약한 경우

### 3라운드: 최종 종합

ChairInvestmentAgent가 각 에이전트의 의견을 종합하여 최종 의견을 정리한다.
이 결과는 `committee_view`로 저장되며, `model_view`와 구분하여 제시한다.

최종 위원회 라벨은 다음과 같이 사용한다.
- `적격`: 모델 판단과 정성 근거를 종합할 때 투자적격으로 보는 경우
- `보류`: 당장 부적격으로 보기는 어렵지만, 추가 점검 또는 보수적 해석이 필요한 경우
- `부적격`: 정량·정성 근거를 종합할 때 투자 위험이 높다고 보는 경우

## 5. 입력 번들 설계

5에이전트에는 원시 CSV 전체를 넘기지 않는다.
정량 모델과 대시보드에서 이미 정리한 설명용 번들을 입력으로 사용한다.

권장 입력 필드:
- 기업명
- 종목코드
- 시장
- 산업
- 규모
- 회계연도
- 예측확률
- 모델 라벨
- SHAP 기반 주요 변수
- 핵심 재무지표
- 시장/산업 비교 결과
- 뉴스 요약
- 공시 요약
- 재무제표 주석 요약
- 현재 금리, 환율, 회사채 스프레드

## 6. 최종 출력 구조

최종 출력은 아래와 같이 이원화한다.

### model_view
- 예측확률(`y_proba`)
- 모델 라벨 (`투자적격` / `부적격`)
- 위험 밴드
- 주요 변수 기여도
- 시장/산업 비교 요약

### committee_view
- 최종 위원회 라벨 (`적격` / `보류` / `부적격`)
- 주요 위험 요인
- 완화 요인
- 외부 근거 기반 보완 판단
- 종합 심사 메모

즉, 사용자는 **모델이 본 이진 판단**과
**에이전트 위원회가 검토한 3단계 종합 의견**을 함께 확인할 수 있다.

## 7. 구현 순서

### 1단계
- Stage 1 결과를 설명용 입력 번들로 정리
- Agent별 역할과 출력 형식 확정
- committee_view 기본 구조 정의

### 2단계
- 뉴스/공시/주석 수집 파이프라인 연결
- Agent별 프롬프트와 출력 템플릿 정의
- 샘플 기업 기준 로컬 테스트 수행

### 3단계
- ChairInvestmentAgent 종합 메모 구현
- 대시보드와 연결
- 심사 메모 다운로드 및 보고서 형식 연동

## 8. 이번 문서의 범위

본 문서는 구현 코드가 아니라 설계 합의를 위한 초안이다.
따라서 다음 항목은 아직 포함하지 않는다.

- 실제 API 키 처리 방식
- 실시간 크롤링 코드
- failover 로직
- HITL 세부 동작
- 위원회 내 라운드별 세부 발화 규칙

이 항목들은 기본 5에이전트 구조가 합의된 이후
별도 구현 단계에서 다룬다.
